# Wire Scan Run Registry KPI Definitions

## Purpose

This document defines the standard KPIs for reporting wire scan system health and activity to senior management.

The goals are:
- Use repeatable, data-based metrics from the Run Registry.
- Keep definitions stable across reporting periods.
- Make each KPI easy to explain in plain language.

## Data Source and Scope

Primary source:
- Run Registry JSON generated by `RunRegistry` during scan operations.

Reporting workflow:
- Snapshot JSON at a fixed cutoff date/time.
- Convert the snapshot to a SQLite file for querying.
- Run the same saved SQL query pack each period.

Default reporting windows:
- Weekly report: previous full Monday-Sunday period.
- Monthly report: previous full calendar month.

## Canonical Fields

The metrics in this document assume each run has these fields:
- run_id
- timestamp (raw)
- method
- wire
- beampath
- detector
- filepath
- plots
- status
- error

For SQL reporting, convert timestamp into `timestamp_iso` in ISO-8601 local time.

## Global KPI Rules

1. Run uniqueness:
- A run is uniquely identified by `run_id`.

2. Success definition:
- A run is successful if `status = "ok"`.

3. Failure definition:
- A run is failed if `status = "error"`.

4. Missing status handling:
- If status is null or unexpected, classify as `unknown` and report separately.

5. Time assignment:
- A run belongs to a period based on `timestamp_iso`.

6. Percentage formatting:
- Use one decimal place for management slides.

## KPI Definitions

### 1) Total Runs

Plain-language definition:
- Total number of run records in the reporting window.

Formula:
- `total_runs = count(all runs in period)`

Why it matters:
- Shows overall scan activity and operational throughput.

### 2) Successful Runs

Plain-language definition:
- Number of runs completed without recorded error.

Formula:
- `successful_runs = count(runs where status = "ok")`

Why it matters:
- Measures delivered scan output, not just attempts.

### 3) Failed Runs

Plain-language definition:
- Number of runs that recorded an error.

Formula:
- `failed_runs = count(runs where status = "error")`

Why it matters:
- Direct reliability signal and incident burden indicator.

### 4) Success Rate

Plain-language definition:
- Percent of runs that completed successfully.

Formula:
- `success_rate = successful_runs / total_runs * 100`

Display note:
- Also show `failed_runs` next to success rate for context.

Why it matters:
- Single top-line health metric for leadership.

### 5) Failure Rate

Plain-language definition:
- Percent of runs that ended in error.

Formula:
- `failure_rate = failed_runs / total_runs * 100`

Why it matters:
- Highlights system reliability risk trend.

### 6) Distinct Wires Scanned

Plain-language definition:
- Number of unique wire devices scanned at least once in the period.

Formula:
- `distinct_wires_scanned = count(distinct wire)`

Why it matters:
- Indicates system coverage breadth.

### 7) Wire Coverage Recency

Plain-language definition:
- For each wire, how long since last scan.

Formula:
- `days_since_last_scan = report_cutoff_date - max(timestamp_iso for wire)`

Standard thresholds:
- Green: 0-7 days
- Yellow: 8-14 days
- Red: 15+ days

Why it matters:
- Exposes stale or unverified parts of the wire scan fleet.

### 8) Runs by Method

Plain-language definition:
- Number of runs by scan method (`otf`, `step`, other).

Formula:
- `count(*) grouped by method`

Why it matters:
- Shows operational mode mix and process usage shifts.

### 9) Failures by Wire

Plain-language definition:
- Failure concentration by device.

Formula:
- `count(failed runs) grouped by wire`

Companion metric:
- `wire_failure_rate = failed_runs_for_wire / total_runs_for_wire * 100`

Why it matters:
- Identifies highest-risk devices for maintenance planning.

### 10) Failures by Beampath

Plain-language definition:
- Failure concentration by accelerator beampath.

Formula:
- `count(failed runs) grouped by beampath`

Why it matters:
- Helps localize operational issues by region.

### 11) Failures by Detector

Plain-language definition:
- Failure concentration by selected detector.

Formula:
- `count(failed runs) grouped by detector`

Why it matters:
- Helps isolate detector-specific reliability problems.

### 12) Top Error Signatures

Plain-language definition:
- Most frequent error messages in the period.

Formula:
- `count(failed runs) grouped by normalized error text`

Normalization rules:
- Trim whitespace.
- Lowercase.
- Remove volatile IDs/timestamps when possible.

Why it matters:
- Distinguishes one-off failures from recurring systemic issues.

### 13) Data File Completion Rate

Plain-language definition:
- Percent of runs with a non-empty `filepath`.

Formula:
- `file_completion_rate = count(runs with filepath) / total_runs * 100`

Why it matters:
- Validates data artifact generation pipeline.

### 14) Plot Completion Rate

Plain-language definition:
- Percent of runs with at least one plot path.

Formula:
- `plot_completion_rate = count(runs with >=1 plot) / total_runs * 100`

Why it matters:
- Validates visualization artifact production for downstream review.

## Executive Dashboard (Recommended)

Primary monthly KPI card set:
- Total Runs
- Success Rate
- Failed Runs
- Distinct Wires Scanned
- Red Wires (15+ days since last scan)
- Top 3 Error Signatures

Secondary diagnostics for appendix:
- Runs by method trend (weekly)
- Failures by wire
- Failures by beampath
- File and plot completion rates

## Data Quality Checks Before Publishing

Run these checks each reporting cycle:
- Count parity: SQLite run count equals JSON snapshot run count.
- Uniqueness: no duplicate `run_id`.
- Status validation: values are `ok`, `error`, or `unknown`.
- Timestamp parse rate: 100 percent converted to `timestamp_iso`.
- Plot integrity: plot row count equals sum of plot-list lengths.

If any check fails:
- Mark report as provisional.
- Include issue and estimated impact in report notes.

## Governance and Change Control

1. Keep KPI definitions stable over time.
2. If a KPI definition changes, annotate effective date and rationale.
3. Version query templates in source control.
4. Preserve immutable period snapshots.
5. Use a fixed cutoff rule every period.

## Suggested Reporting Footnote

"Metrics are computed from immutable Run Registry snapshots converted to SQLite for queryability. Definitions follow the Wire Scan Run Registry KPI Definitions standard."
